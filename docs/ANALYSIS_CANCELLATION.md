# 분석 취소와 정리 확인

관리자는 분석 작업의 취소 버튼 또는 `POST /api/analyses/jobs/{id}/cancel`로 취소를 요청한다. 조회 계정은 상태를 볼 수 있다. 성공한 취소 요청은 기존 감사 미들웨어가 사용자·요청 경로·시각과 함께 기록한다.

| 요청 시 상태 | 응답 상태 | 자산의 다른 분석 |
| --- | --- | --- |
| QUEUED | CANCELLED | 바로 요청 가능 |
| COLLECTING / SCANNING / IMPORTING | CANCEL_REQUESTED | 프로세스 정리 확인까지 차단 |
| CANCEL_REQUESTED / CANCELLED | 기존 상태 반환 | 멱등 요청 |
| SUCCESS / FAILED | 409 | 완료된 결과를 취소로 바꾸지 않음 |

실행 중인 작업은 약 5초 간격의 heartbeat에서 취소를 감지한다. 로컬 도구의 프로세스 그룹과 원격 수집 프로세스를 정리한 뒤 `CANCELLED`로 확정한다. 실제 시간은 SSH 응답과 정리 확인에 따라 더 걸릴 수 있다. 예약 일시 중지는 다음 요청을 막으며 이미 시작한 작업의 취소는 별도로 요청한다.

취소가 결과 import보다 먼저 DB 상태를 확보하면 새 분석 결과를 저장하지 않는다. 결과 저장 트랜잭션이 먼저 확보하면 저장을 마친 뒤 취소가 409를 반환한다. 기존 분석 결과와 원본 ZIP은 보존한다.

`GET /api/analyses/jobs/active`는 대기·실행·취소 요청 상태를 모두 반환한다. 최근 이력 페이지의 100건 제한과 독립적이므로 오래 실행 중인 작업을 계속 추적할 수 있다.

## 운영 확인

worker의 `ANALYSIS_ARTIFACTS_DIR` 아래 `job-{작업번호}-{worker_token}/manifest.json`을 확인한다. 기본 경로는 `/var/lib/eolwatch/analysis`이며 실제 파일은 `analysis_artifacts` 볼륨에 있다. 작업 토큰은 API 응답으로 노출하지 않는다. 관리자는 해당 작업 번호로 시작하는 디렉터리를 찾아 확인한다.

- DB 상태 `CANCELLED`, `finished_at` 기록, `active_asset_id` 해제: 취소 확정.
- manifest의 `cleanup_confirmed: true`와 `finished_at`: executor의 정리 완료 증거. 취소 도중 manifest의 실행 상태는 `interrupted`일 수 있으며 DB의 최종 작업 상태와 구분한다.
- 원격 종료는 작업마다 생성한 `analysis-<UUID>.json` 인자가 해당 PID의 `/proc/.../cmdline`에 있는지 검사한다. 프로세스 그룹이 사라져야 종료 성공으로 인정한다. 연결 종료만으로 원격 실행이 끝났다고 판정하지 않는다.

## worker 중단 후 복구

worker가 정리를 마치고 manifest를 저장한 뒤 DB 반영 전에 중단되면, 재시작한 worker가 오래된 `CANCEL_REQUESTED` 작업의 정리 증거를 확인하여 취소를 확정한다. 기준은 `ANALYSIS_JOB_LEASE_SECONDS`이며 기본 180초이다.

정리 증거가 없거나 실패했다면 `CANCEL_CLEANUP_REQUIRED`가 표시되고 자산 잠금을 유지한다. 이 경우 관리자는 다음을 확인한다.

1. 해당 예약을 일시 중지하고 작업 번호·자산·분석 범위를 확인한다.
2. worker 상태와 해당 작업의 manifest·로그를 확인한다. 다른 작업의 프로세스나 원본 파일은 수정하지 않는다.
3. 원격 연결 문제라면 등록된 신뢰 호스트 키와 접속을 복구한다. worker 재시작만으로 확인되지 않은 원격 프로세스가 종료됐다고 간주하지 않는다.
4. 정상 executor가 정리를 완료해 증거를 남겼다면 worker의 다음 복구 주기에 취소가 확정된다. 증거 없이 강제 종료된 실행은 별도의 관리자 프로세스 복구가 필요하다. 이 버전은 임의 PID 종료·강제 잠금 해제 API를 제공하지 않는다.

manifest를 수동으로 성공 상태로 바꾸거나 DB 잠금을 먼저 지우는 것은 정리 확인을 대신하지 않는다. 불확실한 상태에서는 새 분석과 이전 프로세스가 겹치지 않도록 취소 요청 상태를 유지한다.

## 예약 처리와 검증

예약은 한 번에 최대 50건을 처리하되 마지막 시도가 오래된 만기 예약부터 선택한다. 앞의 50건이 활성 작업과 충돌해도 다음 주기에 뒤의 만기 예약이 처리된다. 이 순서는 DB에 보존되어 worker 재시작 후에도 유지된다. 충돌한 예약의 만기는 계속 보존한다.

Python 3.12 격리 컨테이너에서 취소·작업·executor·입력 관련 focused 테스트 **95개**가 통과했다. 실제 프로세스 그룹 종료, 다른 작업의 PID 보호, 취소와 import 경쟁, 정리 증거 유무에 따른 복구, 100건 초과 활성 작업 조회, 50개 초과 예약 진행을 포함한다. 운영 서비스의 실제 취소 검증은 배포 후 별도로 수행한다.
