# 커널 CVE 과탐 검증과 전체 업데이트 후 재검사 (2026-09-22)

교수님 피드백 두 가지를 실제로 확인한 기록이다.

1. 커널이 다 고쳐진(전체 업데이트한) 우분투를 VM에 올려 CVE를 검사해 본다.
2. 도구가 커널 패키지 이름만 보고 일방적으로 다 잡는 과탐이 아닌지 확인한다.

기준 데이터: srv-my(EC2, Ubuntu 26.04, 검사 #40, 2026-09-22 13:25 KST)의 저장된 Grype 원본 JSON(연결 37,170건), 실습 VM `LAB-VM-02`(VirtualBox, Ubuntu 24.04.5 arm64)의 업데이트 전 검사 #42와 업데이트 후 검사. Grype DB는 세 검사 모두 `v6.1.9 · 2026-09-21T06:39:24Z` 빌드로 같다(`grype db check`: No update available).

## 1. 결론

- Grype는 커널 패키지를 **이름으로 잡지 않는다.** 저장된 원본의 매칭 근거(`matchDetails`)를 보면 커널 바이너리 패키지 37,170건 전부가 `dpkg-matcher`의 `exact-indirect-match`, 즉 PURL의 `upstream=linux-aws` 소스 패키지와 설치 버전을 Ubuntu 26.04 배포판 데이터의 버전 조건(예: `< 7.0.0-1012.12`)에 대조한 결과다. 같은 이름 계열인 최신 커널 7.0.0-1012에는 "수정판 있음" CVE 1,652건이 하나도 붙지 않았다. 이름만 봤다면 붙어야 한다.
- 무작위 표본 80건을 Ubuntu 공식 CVE 추적기(ubuntu.com/security/cves, resolute)와 대조한 결과 **78건이 상태·수정 버전까지 일치**했다. 수정판이 있다고 한 20건은 수정 버전 문자열까지 같았고, 수정판 없다고 한 58건은 Ubuntu도 `needed`/`pending`/`needs-triage`/`deferred`였다.
- 불일치 2건(libexpat1, CVE-2026-50219·CVE-2026-45186)은 **Grype DB 지연**이다. Ubuntu가 2026-09-21 13:50 UTC에 수정판(USN-8790-1, 2.7.4-1ubuntu0.1)을 냈고 서버에는 이미 그 버전이 깔려 있었지만, 검사에 쓴 Grype DB는 같은 날 06:39 UTC 빌드라 아직 몰랐다. 이런 항목은 다음 DB 갱신 후 재검사하면 사라진다. 순수한 과탐은 80건 중 이 2건(2.5%)이고 도구의 판정 논리 문제가 아니라 데이터 시차다.
- 그럼에도 숫자가 큰 이유는 세 가지다. (1) Ubuntu 추적기가 커널 소스 패키지 하나에 수천 개 CVE를 기록하고 그중 대부분이 아직 수정판 없음, (2) 커널 소스에서 나온 바이너리 패키지(linux-modules·linux-tools·linux-aws-tools·bpftool)마다 같은 CVE가 붙어 연결 수가 3~4배, (3) 이전 커널 패키지가 지워지지 않고 남아 있어 그 커널의 CVE까지 잡힌다. 셋 다 "틀린 판정"이 아니라 "패키지 단위 판정"의 성질이며, EOLWatch는 CVE 번호 기준 1회 계산, 커널 분리, 수정판 있음/없음 분리, apt 대조로 이를 읽을 수 있게 만든다.
- 전체 업데이트한 Ubuntu에서도 CVE는 0이 되지 않는다. 2절 참고.

## 2. 피드백 1 — 전체 업데이트한 우분투 VM 검사

실습 VM `eolwatch-target-02`(Ubuntu 24.04.5 LTS, arm64, VirtualBox)를 켜서 EOLWatch에 `LAB-VM-02`로 등록하고, 업데이트 전 검사 → `apt full-upgrade` + 이전 커널 제거 + 재부팅 → 업데이트 후 검사를 같은 Grype DB로 돌렸다.

|---|---|---|

EOLWatch 전후 비교(`GET /api/analyses/42/compare/43`): 계속 검출 14,976 · 새로 검출 0 · **재검사 미검출 16**(CVE 8건: libaom3 4, perl 2, polkit 1, sqlite3 1) · 구성요소 제거 0, 경고 없음(`comparable: true`).

읽는 법:

- 업데이트 전에 "수정판 있음"으로 표시된 8건은 전부 apt가 실제로 올릴 수 있는 것으로 대조됐고(`UPDATE_AVAILABLE` 8), `apt full-upgrade` 뒤 정확히 그 8건만 사라졌다. 도구가 "고칠 수 있다"고 한 것과 실제로 고쳐진 것이 1:1로 맞는다.
- 커널 CVE 3,570건은 그대로다. 이 VM의 커널 6.8.0-139는 24.04 저장소의 최신 후보와 같고 이전 커널 패키지도 없다. 즉 **완전히 업데이트한 Ubuntu에서도 커널 CVE 3,570건이 남으며, 이는 Ubuntu가 아직 수정판을 내지 않은 항목**이다(3-2절 표본의 `needed`/`pending`과 같은 종류).
- srv-my(26.04)와 비교하면, 배포판 버전이 최신인지와 무관하게 "수정판 없음" 커널 CVE는 수천 건 단위로 남는다. srv-my에서 업데이트로 없앨 수 있는 것은 이전 커널 잔존분 1,652건뿐이다.

## 3. 피드백 2 — 이름만 보고 잡는 과탐인가

### 3-1. 매칭 근거: 소스 패키지 + 버전 조건

srv-my 검사 #40의 Grype 원본에서 커널 바이너리 한 건의 매칭 근거다.

```json
{"type": "exact-indirect-match", "matcher": "dpkg-matcher",
 "searchedBy": {"distro": {"type": "ubuntu", "version": "26.04"},
                "package": {"name": "linux-aws", "version": "7.0.0-1006.6"}},
 "found": {"vulnerabilityID": "CVE-2026-53362", "versionConstraint": "< 7.0.0-1012.12 (deb)"},
 "fix": {"suggestedVersion": "7.0.0-1012.12"}}
```

검출된 패키지는 `linux-modules-7.0.0-1006-aws`지만 대조한 것은 PURL `upstream=linux-aws`가 가리키는 **소스 패키지 linux-aws의 버전 7.0.0-1006.6**이고, 조건은 Ubuntu가 공개한 수정 버전 `7.0.0-1012.12` 미만이다. 원본 37,170건의 매칭 근거는 다음 세 가지뿐이다.

| 대조한 소스 패키지·버전 | 연결 건수 | 실제 검출 바이너리 |
|---|---|---|
| linux-aws 7.0.0-1006.6 (이전 커널) | 14,322 | linux-modules/linux-tools/linux-aws-tools-7.0.0-1006 |
| linux-aws 7.0.0-1012.12 (최신 커널) | 12,488 | linux-aws, linux-modules/linux-tools/linux-aws-tools-7.0.0-1012 |
| linux 7.0.0-31.31 (커널 도구) | 9,378 | linux-tools-common, linux-perf, bpftool |

"이름만 보고 잡는다"면 이전 커널에 붙은 수정판 있음 CVE 1,652건이 최신 커널 1012에도 그대로 붙어야 한다. 실제로는 1012에 붙은 3,122건은 전부 "수정판 없음"이고 1,652건은 1006에만 있다. 버전 조건이 작동한다는 뜻이다.

### 3-2. Ubuntu CVE 추적기와 표본 대조 (80건)

검사 #40의 CVE를 네 묶음으로 나눠 각 20건을 무작위(seed 7)로 뽑고, `https://ubuntu.com/security/cves/<CVE>.json`에서 같은 소스 패키지의 resolute(26.04) 상태를 읽어 비교했다(스크립트는 세션 스크래치, 결과는 아래 표).

| 묶음 | 모집단 | 표본 | 일치 | 불일치 |
|---|---|---|---|---|
| A 이전 커널(linux-aws 1006) 수정판 있음 | 1,652 | 20 | 20 (수정 버전 문자열까지 동일: 1008.8 / 1009.9 / 1010.10 / 1012.12) | 0 |
| B 최신 커널(linux-aws 1012) 수정판 없음 | 3,122 | 20 | 20 (Ubuntu: needed 12, pending 7.0.0-1014.14 8) | 0 |
| C 커널 도구(linux 7.0.0-31.31: bpftool·linux-perf·linux-tools-common) | 3,126 | 20 | 20 (needed 8, pending 12) | 0 |
| D 커널 아닌 일반 패키지 | 407 | 20 | 18 (needs-triage 15, needed 2, deferred 1) | 2 (libexpat1: Ubuntu는 released 2.7.4-1ubuntu0.1, 설치 버전과 동일 → DB 지연) |

B·C의 `pending 7.0.0-1014.14`는 Ubuntu가 다음 커널에서 고칠 예정이라는 뜻이라 지금 시점에서는 "수정판 없음"이 맞다. 표본 상세는 이 문서 끝의 부록에 있다.

### 3-3. 그래도 숫자가 큰 이유

1. **소스 패키지 단위 추적.** Ubuntu는 커널 소스 `linux`/`linux-aws`에 대해 CVE 상태를 기록한다. 그 소스에서 나온 바이너리 패키지가 여러 개(모듈·도구·헤더·bpftool)라 같은 CVE가 패키지마다 붙는다. 검사 #40에서 CVE 번호 기준 5,150건이 연결 기준으로는 37,170건이 되는 이유다. EOLWatch는 CVE 번호마다 한 번만 세고(`cve_count`), "CVE별로 보기"에서 패키지를 접는다.
2. **수정판 없는 CVE.** 커널 CVE 4,778건 중 3,126건은 Ubuntu가 아직 고치지 않은 것이다. 이는 "고칠 수 있는 것"과 분리해 보여 준다("지금 고칠 수 있는 CVE n개(커널 제외)").
3. **이전 커널 잔존.** srv-my에는 7.0.0-1006과 7.0.0-1012 커널이 함께 설치돼 있었고 실행 커널은 1006이었다. 1006에 붙은 4,774건 중 1,652건은 1012에서 이미 고쳐진 것이다. `apt autoremove --purge`로 이전 커널을 지우면 사라진다. 도구는 "설치된 패키지"를 보므로 실행 중이 아닌 커널도 잡는다. 이것은 과탐이 아니라 "설치돼 있으면 잡는" 정책이며, 실제 노출은 실행 커널 하나다.
4. **커널 도구 패키지.** `linux-tools-common`·`linux-perf`·`bpftool`은 사용자 공간 도구인데 커널 소스 `linux`(generic)에서 나오므로 커널 CVE 3,126건이 그대로 붙는다. 이 서버에는 generic 커널이 설치돼 있지 않아 실제 노출과 가장 거리가 먼 항목이다. 다만 Ubuntu 추적기도 소스 `linux`를 affected로 표시하므로 도구 판정 자체는 추적기와 일치한다. 이 3,126건은 최신 커널 linux-aws 1012의 3,122건과 4건을 빼고 같은 CVE라 CVE 번호 기준으로는 중복이다.

### 3-4. EOLWatch가 이미 하는 것과 이번에 확인한 한계

- 하는 것: pkg:deb PURL과 `--distro ubuntu:<버전>`으로 배포판 데이터만 대조(CPE 대조 끔), CVE 번호 기준 집계, 커널/일반 분리, 수정판 있음/없음 분리, 검사 직후 apt 대조(`UPDATE_AVAILABLE`/`NO_UPDATE_FOUND`), CVE별 접기.
- 한계 1: Grype DB가 Ubuntu 공지보다 최대 하루 늦다. libexpat1 2건처럼 "이미 고쳐졌는데 DB가 모르는" 항목은 apt 대조로도 못 잡는다(Grype가 수정판을 모르니 대조할 버전이 없다). 개선안: 수정판 없음 CVE 중 설치 버전이 Ubuntu 추적기의 `released` 버전 이상인 것을 추적기 API로 재확인하는 단계.
- 한계 2: 실행 커널과 설치 커널을 구분하지 않는다. SSH 점검의 `uname -r`과 검사 결과를 묶어 "실행 중 아님"을 표시하는 개선이 가능하다.
