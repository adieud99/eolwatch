# EOLWatch 웹 사용 안내

코드 기준: 2026-09-15 기능 확장. 실제 실습 결과와 화면 근거는 [확장 검증 기록](PROJECT_EXPANSION_VERIFICATION.md)에 기록한다. 관리 VM 웹은 <http://127.0.0.1:18080>, 맥 Docker 웹은 <http://127.0.0.1:8080>이며 두 DB는 별개다.

## 1. 자산 준비

`고객·사이트`에서 조직 정보를 확인하고 `작업 대상`에서 결과를 연결할 자산을 등록하거나 수정한다. SSH 분석에는 관리 IP·SSH 계정·모니터링 사용과 관리 서버의 키·known_hosts가 필요하다. ZIP 분석에는 연결할 자산이 필요하며 해당 자산으로 SSH 접속하지 않는다.

`제품·계약`에서는 제품의 지원 일정·공식 근거·영향 자산을 조회하고 계약과 대상 자산을 연결한다. 제품/계약 변경과 분석 실행은 관리자 권한이며 조회자는 결과를 읽을 수 있다.

재고자산 관리는 `작업 대상 자산`에서 수행한다. 자산명·자산번호·모델·시리얼·건물·층·랙·구매가격·전력·담당자·운영 상태·서비스 중요도를 입력할 수 있으며, 목록 검색과 위험 우선순위에서 분석 결과와 함께 확인한다. 자산 상세에서는 설치 소프트웨어·SBOM·분석/점검/CVE 조치 타임라인·QR·자산 PDF를 제공한다.

새 자산 위험 이력 테이블을 적용해야 하는 환경에서는 관리 API 컨테이너가 실행되는 상태에서 다음을 먼저 실행한다.

```bash
docker compose exec api alembic upgrade head
```

Docker Compose가 실행되지 않는 경우에는 이 명령을 실행했다고 설명하지 않고, 애플리케이션 코드와 테스트 검증 결과만 구분해 제시한다.

## 2. 프로젝트 소스 ZIP 분석

1. `프로젝트 분석` → `소스 ZIP 업로드`를 선택한다.
2. 결과를 연결할 자산과 프로젝트 이름을 입력한다.
3. 잠금 파일·패키지 명세가 포함된 ZIP을 선택하고 `지금 분석 시작`을 누른다.
4. `CVE 조치`에서 작업 상태를 확인한다. 완료되면 해당 SBOM 결과가 선택된다.
5. 다음 버전도 같은 자산·프로젝트 이름으로 올리면 같은 범위의 전후 분석으로 비교할 수 있다.

기본 최대 업로드는 50 MiB다. 해제 합계 250 MiB, 파일당 32 MiB, 20,000항목과 압축률 100배 한도가 있다. 경로 이탈·심볼릭 링크·특수 파일·암호화 ZIP·중복 경로를 거부한다. 원본을 SHA-256으로 보관하고 분석·재시도 전에 다시 검증한다.

프로젝트를 실행·빌드하거나 의존성을 설치하지 않는다. 소스에 포함된 자료가 선언된 의존성인지 실제 설치 메타데이터인지 확인해 결과를 해석한다. 내부의 중첩 압축 파일과 `.git`은 탐색에서 제외한다. ZIP이라고 해서 모든 소프트웨어를 자동으로 식별할 수 있는 것은 아니다.

저장소 자체를 명세·소스 ZIP으로 준비하는 보조 명령:

```bash
python3 scripts/package-project-source.py
```

출력은 `reports/eolwatch-project-source.zip`이다. 이 스크립트는 명시한 소스·패키지 명세만 묶으며 전체 작업 디렉터리나 환경설정·개인키를 압축하지 않는다. 실제 분석 요청은 위 웹 흐름으로 수행한다.

## 3. 등록 서버의 앱 경로 분석

`프로젝트 분석` → `서버 앱 경로`에서 자산과 방식을 선택한다.

| 웹 선택 | 입력 | 의미 |
|---|---|---|
| 서버 프로젝트 폴더 | 예: `/opt/my-app` | 폴더에 있는 설치·선언 의존성 자료 |
| 서버 Python 가상환경 | 예: `/opt/my-app/.venv` | 설치 Python 패키지 메타데이터 |
| Ubuntu 설치 패키지 | 경로 입력 없음 | dpkg 설치 패키지 |
| 기존 Python 데모 앱 | 경로 입력 없음 | SSH 계정의 `~/eolwatch-demo/.venv` |

경로 방식은 상위 이동(`..`) 없는 실제 절대 경로를 사용한다. 루트 `/`, 제어 문자, 다른 경로로 연결되는 심볼릭 링크는 허용하지 않는다. SSH 계정이 읽을 수 있어야 하며 대상과 worker는 같은 CPU 아키텍처의 Linux arm64 또는 amd64여야 한다.

`작업 대상`에 있는 기존 빠른 분석 버튼으로 OS·데모 분석을 요청할 수도 있다. CPU·메모리·디스크의 `SSH 점검`은 취약점 분석과 별개다.

## 4. 정기 분석

서버 분석 방식·자산·경로와 주기(5~525600분)를 선택하고 `정기 분석 등록`을 누른다. 아래 `정기 분석` 표에서 다음 실행·최근 작업·오류를 확인하고 주기 저장, 일시 중지, 다시 실행을 사용할 수 있다.

예약은 DB에 저장되며 worker가 기한이 되면 기존 분석 큐에 요청한다. 같은 자산·범위의 예약을 중복 등록할 수 없다. 중단 동안 밀린 횟수를 모두 실행하지 않으며 진행 중인 작업과 충돌하면 다음 확인에서 처리한다. ZIP 재분석 예약은 제공하지 않는다. 변경된 ZIP은 새 파일로 업로드한다.

## 5. 결과 탐색과 조치

- `운영 개요`: 자산·범위별 마지막 성공과 최근 요청, 누적 미완료 CVE를 구분한다.
- `SBOM 원장`: 상세에서 구성요소 검색·페이지 이동, 라이선스·해시·PURL, 들어오는/나가는 의존관계, 원본 JSON을 확인한다.
- 구성요소 지원 종료일은 개별 설정을 우선 사용한다. 개별 날짜를 해제하면 연결 제품의 지원 일정으로 돌아간다. 날짜와 공식 근거 URL을 함께 관리한다.
- `CVE 조치`: 선택한 SBOM의 결과를 서버 페이지로 조회하고 같은 자산·범위의 분석을 비교한다.
- `조치 작업목록`: 검색, 자산·담당자·미지정·상태·심각도·기한 초과 조건으로 전체 SBOM 이력의 업무를 찾는다. 정렬은 미완료 기한 초과 → 심각도 → 조치 번호다.
- `조치 관리`: 담당자·기한·메모·재분석 근거와 상태를 저장한다. 다른 운영자의 수정과 충돌하면 최신 변경을 확인한 후 다시 저장한다. 조회자는 이력만 읽는다.
- 전후 비교의 `검증 보고서 PDF`·`검증 데이터 JSON`으로 분석 근거를 내려받는다.

미검출과 운영자의 완료 판단은 구분한다. CVE를 검출한 과거 SBOM과 조치 이력은 다음 분석이 0건이어도 유지한다. OSV 추가 조회는 설치 버전·생태계·구간에 맞는 수정 버전을 계산하며, 버전 없는 항목·철회·비해당 결과의 개수를 별도로 보여준다. 부분 응답이나 외부 조회 실패를 정상 0건으로 처리하지 않는다.

## 6. 진행·실패·재시도

상태는 `QUEUED` → `COLLECTING` → `SCANNING` → `IMPORTING` → `SUCCESS`다. 실패는 `FAILED`와 오류 코드·메시지로 남는다. 실패 원인을 해결한 뒤 `재시도`하면 새 작업이 만들어지며 이전 실패는 유지한다. ZIP은 보관한 같은 원본을 사용한다.

같은 자산의 다른 범위가 실행 중이면 완료 후 요청한다. 빈 수집, 잘못된 원본, 접속 대상 변경, 원본 해시 불일치는 실패다. 정상 구성요소와 명시적 빈 Grype 결과는 CVE 0건으로 저장할 수 있다. 창 이동이나 API 재시작으로 DB 작업 이력이 사라지지 않는다.
