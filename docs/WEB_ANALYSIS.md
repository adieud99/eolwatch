# EOLWatch 웹 사용 안내

코드 기준: 2026-09-21. 관리 VM 웹은 <http://127.0.0.1:18080>, 맥 Docker 웹은 <http://127.0.0.1:8080>이며 두 DB는 별개다. 메뉴는 `개요`, `개발 검사`, `인프라 검사`, `검사 기록` 네 개다.

## 1. 개발 검사 — 소스 ZIP · 의존성 파일 · Git 저장소

입력 방법은 세 가지다. 어느 방법이든 결과는 선택한 서버(대상)와 프로젝트 이름으로 묶이며, 그 서버에 SSH 접속하지 않는다.

| 입력 | 사용 | 검사 범위 이름 |
|---|---|---|
| 소스 ZIP | 잠금 파일·패키지 명세가 든 소스 ZIP 선택 | `source-zip:<프로젝트>` |
| 의존성 파일 | `requirements.txt`, `package-lock.json`, `pom.xml`, `go.sum`, `Gemfile.lock`, `Cargo.lock`, `composer.lock` 같은 파일 하나만 선택. 서버가 그 파일만 담은 ZIP으로 보관한다 | `source-zip:<프로젝트>` (같은 이름의 ZIP 검사와 비교 가능) |
| Git 저장소 | `Git 저장소` 탭에서 https 주소·브랜치(또는 태그)·비공개 저장소 토큰 입력. worker가 최신 커밋만 얕게 읽기 전용으로 복제한 뒤 같은 방식으로 검사한다 | `source-git:<프로젝트>` |

1. `개발 검사`에서 결과를 연결할 서버와 프로젝트 이름을 입력한다.
2. ZIP이나 의존성 파일을 선택하거나, `Git 저장소` 탭에서 주소를 입력하고 검사를 시작한다.
3. 아래 `소스 검사 작업` 표에서 대기 → 수집 → 분석 → 저장 → 완료 상태를 확인한다. 완료되면 `결과 보기`로 CVE 결과를 연다.
4. 다음 버전도 같은 서버·프로젝트 이름으로 올리면 같은 범위의 전후 검사로 비교할 수 있다.

기본 최대 업로드는 500 MiB다. 해제 합계 2 GiB, 파일당 256 MiB, 200,000항목과 압축률 100배 한도가 있다. 경로 이탈·심볼릭 링크·특수 파일·암호화 ZIP·중복 경로를 거부한다. 원본을 SHA-256으로 보관하고 검사·재시도 전에 다시 검증한다.

Git 저장소는 `git clone --depth 1`로 서브모듈·태그 없이 받으며, 복제한 커밋 해시를 작업에 기록한다. 토큰은 복제 한 번에만 쓰고 저장하지 않으며 작업 기록·로그·원본 파일에 남지 않는다. 저장소 크기 한도는 250 MiB다. 복제 실패는 `GIT_CLONE_FAILED`로 표시한다.

프로젝트를 실행·빌드하거나 의존성을 설치하지 않는다. 소스에 포함된 자료가 선언된 의존성인지 실제 설치 메타데이터인지 확인해 결과를 해석한다. 내부의 중첩 압축 파일과 `.git`은 탐색에서 제외한다. ZIP이라고 해서 모든 소프트웨어를 자동으로 식별할 수 있는 것은 아니다.

저장소 자체를 소스 ZIP으로 준비하는 보조 명령:

```bash
python3 scripts/package-project-source.py
```

출력은 `reports/eolwatch-project-source.zip`이다. 이 스크립트는 명시한 소스·패키지 명세만 묶으며 전체 작업 디렉터리나 환경설정·개인키를 압축하지 않는다.

## 2. 인프라 검사 — 서버

### 접속 방법: SSH 키 또는 비밀번호

서버 등록·수정 화면의 `인증 방식`에서 고른다.

| 방식 | 준비할 것 | 호스트 키 검증 |
|---|---|---|
| SSH 키 (기본) | 관리 서버의 `secrets/eolwatch_ssh_key`와 `secrets/known_hosts`에 대상 서버 공개키·호스트 키 등록 | known_hosts로 엄격 검증 |
| 비밀번호 | 서버 등록 때 SSH 비밀번호 입력. 관리 서버 키·known_hosts 불필요 | 처음 접속 때 서버의 호스트 키를 기억(TOFU)하고 이후 바뀌면 `HOST_KEY_CHANGED`로 거부. 서버를 재설치했으면 서버 수정에서 `호스트 키 초기화` |

비밀번호는 `CREDENTIAL_KEY`(없으면 `JWT_SECRET`)로 파생한 키로 암호화해 저장하고 API 응답·작업 기록·로그에 나오지 않는다. 주소나 포트를 바꾸면 기억한 호스트 키는 지워지고 다음 접속 때 다시 기억한다. 키 방식이 더 안전하므로 시연·임시 서버에만 비밀번호를 쓰고, 운영 서버는 키를 배포하는 편이 좋다.


### 서버 등록

`인프라 검사` → `검사 대상 서버`에서 서버 번호, 서버 이름, 유형, 서버 IP, SSH 포트(기본 22), SSH 계정을 입력하고 `검사 대상으로 사용`을 켠다. 관리 서버에는 SSH 키와 known_hosts가 필요하다. 등록 후 `수정`으로 접속 정보를 바꾸거나 서버를 삭제할 수 있다. 조회자는 `상세`만 볼 수 있다.

### SSH 점검 — 서버 정보 수집

서버 행의 `SSH 점검`은 SSH로 접속해 CPU·메모리·디스크 사용률, 가동 시간, 프로세스, 설치 패키지, OS와 서버 정보(호스트·커널·CPU 모델·메모리 총량·디스크 총량·가상화·클라우드·IP·수신 포트·실행 서비스)를 수집한다. 결과는 서버 목록의 `서버 정보` 열(OS·코어·메모리·실행 환경·클라우드 인스턴스)과 아래 `서버 정보 수집 이력` 표에 표시한다. 수집 이력의 `서버 정보` 버튼을 누르면 호스트·OS·하드웨어·실행 환경·통신 정보·실행 서비스 카드가 열린다. 원본 전체는 `GET /api/checks/{job_id}/result`의 `raw_metrics.server_info`에 있다.

### 개발 검사의 대상

소스 ZIP·의존성 파일·Git 저장소 검사 결과는 "대상" 아래에 프로젝트 이름으로 쌓인다. 대상은 서버일 수도 있고, 서버 주소 없이 결과만 모아 두는 이름일 수도 있다. 후자는 개발 검사 화면의 `+ 새 대상`으로 번호와 이름만 넣어 만들며, 만들자마자 선택된다. 서버 주소·SSH 계정이 필요한 대상은 인프라 검사에서 등록한다. 서버 유형은 서버·가상머신·클라우드 세 가지다.

### CVE 개수 읽는 법 — 수정판 있음과 커널

Ubuntu 서버의 OS 설치 패키지 검사는 CVE가 수천 개로 나올 수 있다. 새로 만든 EC2도 마찬가지인데, Grype가 Ubuntu CVE 추적기의 항목을 설치 소스 패키지마다 전부 대조하기 때문이다. 두 가지가 숫자를 키운다. 첫째, 커널 소스 패키지 `linux` 하나에 수천 개의 CVE가 묶여 있고 커널에서 나온 바이너리 패키지(linux-image·linux-modules·linux-tools·bpftool 등) 각각에 같은 CVE가 연결된다. 둘째, Ubuntu가 아직 고치지 않았거나 고치지 않기로 한 CVE(`수정판 없음`)까지 센다. 그래서 검사 결과 표는 `CVE 전체 · 수정판 있음`을 함께 보여 주고, 아래 줄에 `커널(linux) n개(수정판 m)`과 `수정판 없음`을 따로 적는다. CVE 목록은 기본으로 커널을 제외하며 `수정판 있는 CVE만`을 고르면 `apt upgrade`로 바로 없앨 수 있는 항목만 남는다. 검사 전후 비교로 업데이트 뒤 줄어든 것을 확인하는 흐름이 시연에 알맞다.

### 오탐 대책 — 배포판 데이터와 패키지 관리자 대조

버전 번호만 보고 판정하는 스캐너는 배포판이 버전을 올리지 않고 보안 패치를 백포트한 경우를 취약하다고 잘못 판정(오탐)할 수 있다. EOLWatch는 두 겹으로 막는다. 첫째, OS 설치 패키지 검사는 Grype에 배포판과 버전(`--distro ubuntu:26.04`)을 넘겨 Ubuntu가 공개한 *패키지 버전 기준*의 수정 정보로만 대조한다. 그래서 수정판이 `3.5.5-1ubuntu3.2`처럼 Ubuntu 리비전으로 나오고, 업스트림 버전만 보는 CPE 대조는 쓰지 않는다. 둘째, 검사 직후 워커가 서버의 패키지 관리자에게 실제로 올릴 수 있는 버전을 묻는다(`apt list --upgradable`, `dnf check-update`; 패키지 목록 갱신 외에는 읽기 전용). 수정판이 있다고 나온 CVE마다 저장소의 후보 버전과 수정판을 dpkg 규칙으로 비교해 결과를 남긴다.

| 표시 | 뜻 |
|---|---|
| 저장소에 업데이트 있음 | 저장소가 수정판 이상의 버전을 제공한다. `apt upgrade`로 해결된다 |
| 업데이트는 있지만 수정판 미만 | 더 높은 버전이 있지만 아직 수정판에 못 미친다 |
| 저장소에 업데이트 없음 · 오탐 의심 | 올릴 것이 없는데 취약하다고 나왔다. Grype DB가 미러보다 앞서 있거나 오탐이다. 담당자가 확인한 뒤 조치 상태를 `영향 없음`으로 기록한다 |

검사 결과 표의 `apt 대조: 저장소에 업데이트 있음 n개 · 오탐 의심 m개`가 이 대조의 요약이고, 구성요소 행과 CVE 행에도 같은 표시가 붙는다. 소스 검사(ZIP·Git)는 애플리케이션 의존성이라 패키지 관리자 대조가 없다.

### 검사 안의 AI — 라이브러리 참조와 수집 에이전트

개발 검사에서 올린 소스에 잠금 파일이 없으면(예: `package.json`만 있고 `package-lock.json`이 없거나 `requirements.txt`가 없는 Python 소스) 워커가 소스의 import 문과 의존성 파일 앞부분을 AI에 보여 주고 라이브러리 이름과 버전을 추정하게 한다. 추정 목록은 형식을 검증한 뒤 SPDX로 만들어 Grype로 대조하므로 결과 표에는 `AI 라이브러리 참조 · 버전 추정` 표시가 붙고, 원본 보기의 SPDX에는 구성요소마다 신뢰도와 근거가 남는다. 버전이 추정값이므로 실제 설치 버전 확인이 첫 조치다. AI가 꺼져 있으면 예전처럼 `EMPTY_COLLECTION`으로 끝난다.

SSH 점검에서는 고정 수집(자원·패키지·서버 정보)이 끝난 뒤 AI가 OS·플랫폼·포트·서비스를 보고 읽기 전용 점검 명령을 카탈로그에서 고른다(미적용 보안 업데이트, 재부팅 대기, SSH 정책, 방화벽, 런타임·웹 서버 버전 등). 카탈로그 밖 명령은 실행되지 않는다. 결과는 `서버 정보 수집 이력 → 서버 정보`의 `수집 에이전트` 항목에서 항목별로 펼쳐 볼 수 있고, AI가 없으면 OS 규칙으로 고른 기본 점검이 실행된다.

### AI 요약 — 검사 결과와 서버 진단

`검사 기록 → CVE 결과·조치`에서 SBOM을 고르면 아래에 `AI 요약 · 검사 결과` 카드가 나온다. 관리자가 `AI 요약 생성`을 누르면 그 검사의 CVE 목록(번호·구성요소·버전·수정 버전·심각도)을 설정한 AI 제공자(기본 OpenAI 호환)에 보내 전체 위험 수준, 먼저 손볼 구성요소, 확인할 점을 한국어로 정리해 저장한다. 인프라 검사의 `서버 정보 수집 이력`에서 `서버 정보`를 펼치면 `AI 요약 · 서버 진단` 카드가 있고, 같은 방식으로 환경 요약과 다음 할 일을 만든다. 생성한 요약은 다시 열어도 남아 있고 `다시 생성`으로 갱신한다.

기본 AI는 OpenAI이고 `.env`의 `OPENAI_API_KEY`·`OPENAI_MODEL`을 쓴다. 키가 없으면 버튼이 꺼지고 키를 넣으라는 안내가 나온다. 카드 아래에는 어느 AI가 답했는지와 보낸 글자 수·토큰 수가 표시된다. 데이터는 압축해서 보내며(라이브러리별 묶음, 목록 상한, 패키지는 건수만) 토큰·소스·비밀번호는 보내지 않는다. 결과는 참고 자료이고 조치 상태를 바꾸지 않는다.

### 취약점 검사

서버 행에서 검사 범위를 고르고 `취약점 검사`를 누른다.

| 화면 선택 | 실제 검사 대상 |
|---|---|
| OS · 설치 패키지 | dpkg 설치 패키지 |

worker가 Syft를 서버에 복사해 실행하고, 결과를 SPDX 2.3으로 바꿔 Grype로 검사한다. 진행 상태는 `서버 검사 작업` 표에 나타나고 완료되면 `결과 보기`로 CVE 결과를 연다. 서버 행의 `이력`·`CVE`·`SBOM` 버튼은 검사 기록의 해당 화면으로 이동한다.

대상은 Ubuntu 또는 Debian(x86_64·arm64)이며 worker가 대상 CPU에 맞는 Syft를 고른다. 서버의 앱 경로 검사와 정기 검사 예약은 제공하지 않는다.

## 3. 검사 기록

`검사 기록` 상단의 탭으로 화면을 바꾼다.

| 탭 | 내용 |
|---|---|
| 검사 이력 | 서버·범위별 프로젝트 목록, 검사 결과·작업 이력 검색과 페이지 이동, 취소, 이전·이후 검사 선택 후 비교 |
| CVE 결과·조치 | 선택한 SBOM의 CVE를 서버 페이지로 조회, 수정 버전·심각도·조치 상태, `조치 관리`(관리자) / `조치 이력`(조회자) |
| 의존성 목록 | 선택한 SBOM의 구성요소 검색·페이지 이동, 라이선스·해시·PURL, 원본 JSON 다운로드 |
| 검사 전후 비교 | 같은 서버·범위의 이전·이후 검사 비교, `검증 보고서 PDF`·`검증 데이터 JSON` 다운로드 |

`의존성 목록`과 `검사 전후 비교` 탭은 결과를 선택했을 때 나타난다. 조치 관리에서는 상태와 메모를 저장한다. 다른 운영자의 수정과 충돌하면 최신 변경을 확인한 후 다시 저장한다.

미검출과 운영자의 완료 판단은 구분한다. CVE를 검출한 과거 SBOM과 조치 이력은 다음 검사가 0건이어도 유지한다.

## 4. 개요와 관리

- `개요`: 등록 서버 수, SBOM·구성요소·의존관계 수, 미조치 CVE(전체 이력 기준과 현재 기준), 최근 24시간 실패한 SSH 점검, 서버·범위별 최근 검사와 마지막 성공·최근 요청 상태.
- 계정 관리(관리자/조회자 생성, 역할·활성 변경)와 감사 로그는 API로만 제공한다.

## 5. 진행·실패·재시도

상태는 `QUEUED` → `COLLECTING` → `SCANNING` → `IMPORTING` → `SUCCESS`다. 실패는 `FAILED`와 오류 코드·메시지로 남는다. 실패 원인을 해결한 뒤 `재시도`하면 새 작업이 만들어지며 이전 실패는 유지한다. ZIP은 보관한 같은 원본을 사용한다. 취소는 대기 중이면 즉시 `CANCELLED`, 실행 중이면 `CANCEL_REQUESTED`를 거쳐 프로세스 종료 확인 후 `CANCELLED`다.

같은 서버의 다른 범위가 실행 중이면 완료 후 요청한다. 빈 수집, 잘못된 원본, 접속 대상 변경, 원본 해시 불일치는 실패다. 정상 구성요소와 명시적 빈 Grype 결과는 CVE 0건으로 저장할 수 있다. 창 이동이나 API 재시작으로 DB 작업 이력이 사라지지 않는다.

## 6. 시연과 운영 확인

데모 앱 업데이트 전후 재현은 [조치 시연 안내](REMEDIATION_DEMO.md)를 따른다. 2026-09-15 검증의 LAB-VM-01 검사 #3 → #4는 Jinja2 3.1.4 → 3.1.6에서 앱 범위 CVE 3 → 0이었다. 재실행 번호와 현재 취약점 DB의 건수는 새 결과에서 확인한다.

[교수님용 시나리오](PROFESSOR_PROJECT_GUIDE.md)는 개발 검사·인프라 검사·검사 기록 순서로 화면을 제시한다. [다음 세션 안내](NEXT_SESSION.md)는 서비스 갱신·검사와 DB·ZIP 백업 검증 명령을 정리한다.

컨테이너 이미지 입력, 자동 패치, 공개 다중 고객 서비스는 제공하지 않는다. 상세 요청·응답 규칙은 [API 안내](API.md), 도구·DB·볼륨 구조는 [전체 구조](ARCHITECTURE.md)를 참고한다.
