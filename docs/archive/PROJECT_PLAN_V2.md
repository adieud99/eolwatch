# EOLWatch 2차 기획안 — 인프라 중심 SBOM 통합 수명주기 관리

## 0. 회사 및 프로젝트 맥락

이 프로젝트는 시스원의 인프라 관련 업무를 염두에 둔 학교 파이널 프로젝트다. 시스원은 공개 홈페이지에서 시스템·인프라·관리도구 등 IT 자원의 유지관리와 시스템 통합유지관리 서비스를 사업 영역으로 소개한다. 따라서 EOLWatch의 중심 사용자는 애플리케이션 개발자가 아니라 여러 고객 환경의 서버·스토리지·네트워크와 인프라 소프트웨어를 관리하는 유지보수 엔지니어다.

- [시스원 ITO 사업 소개](https://www.sysone.co.kr/businesses_veiw.php?idx=6)
- [시스원 유지보수 서비스 소개](https://www.siidc.com/outsourcing/maintenance/index.php)

이 문서는 공개된 사업 영역과 일반적인 인프라 유지관리 업무를 바탕으로 작성했다. 시스원의 실제 내부 절차, 고객 정보 또는 기존 관리 시스템을 알고 있다고 가정하지 않으며 시스원의 공식 제품 기획도 아니다.

## 1. 변경 배경

1차 기획은 서버·스토리지·네트워크 장비의 제조사 EOL/EOSL과 유지보수 계약을 관리하는 데 초점이 있었다. 이 방식만으로는 장비 안에서 동작하는 운영체제, 미들웨어, 애플리케이션, 오픈소스 라이브러리의 버전과 지원종료 위험을 알 수 없다.

2차 기획에서는 물리 자산 대장과 SBOM을 연결한다. 예를 들어 `DB 서버 SRV-001 → Ubuntu 22.04 → PostgreSQL 16 → OpenSSL 3.x`처럼 어느 장비에 어떤 운영체제·미들웨어·라이브러리가 있는지 추적한다. 특정 인프라 소프트웨어의 지원이 끝나거나 취약점이 발견되면 영향을 받는 서버를 역방향으로 찾을 수 있다.

## 2. 용어와 적용 기준

- **EOL**: 제품의 판매·개발 등이 종료되는 시점. 공급사마다 정의가 다르므로 원문 출처를 함께 저장한다.
- **EOSL/Support End**: 기술지원, 보안 업데이트, 부품 공급 등이 종료되는 시점. 위험도 계산의 기준일로 사용한다.
- **SBOM**: 소프트웨어를 구성하는 제품·라이브러리와 의존관계를 기계가 읽을 수 있게 표현한 명세서다.
- **HBOM**: 물리 하드웨어와 내부 구성품을 표현하는 명세서다.
- **xBOM**: SBOM, HBOM, SaaSBOM, OBOM 등 여러 BOM 유형을 함께 부르는 표현이다.

이 프로젝트의 교환 형식은 **CycloneDX JSON 1.4~1.7**로 정한다. CycloneDX는 구성요소, 서비스, 하드웨어, 의존관계를 하나의 객체 모델에서 표현할 수 있어 기존 물리 자산 기획을 확장하기 적합하다. 다만 1차 구현에서는 물리 자산을 자체 자산 대장으로 관리하고, SBOM의 소프트웨어 구성요소와 연결한다. CycloneDX HBOM 파일의 완전한 가져오기는 후속 범위다.

구체적인 구성은 [시스템 아키텍처](../ARCHITECTURE.md), [전체 ERD](../DATA_MODEL.md), [기술 스택](../TECH_STACK.md)을 구현 기준으로 사용한다.

참고 기준:

- [CycloneDX Specification Overview](https://cyclonedx.org/specification/overview/)
- [CycloneDX SBOM Capability](https://cyclonedx.org/capabilities/sbom/)
- [CycloneDX HBOM Capability](https://cyclonedx.org/capabilities/hbom/)
- [CISA 2025 SBOM Minimum Elements](https://www.cisa.gov/sites/default/files/2025-08/2025_CISA_SBOM_Minimum_Elements.pdf)

## 3. 프로젝트 정의

**한 줄 정의:** 서버·스토리지·네트워크 등 인프라 자산과 그 위의 운영체제·미들웨어·펌웨어를 연결해 지원종료 위험과 운영 상태를 함께 관리하는 통합 유지관리 시스템

핵심 질문은 세 가지다.

1. 지원이 종료됐거나 임박한 하드웨어와 소프트웨어는 무엇인가?
2. 위험한 소프트웨어 구성요소가 실제로 어느 서버와 서비스에 배포되어 있는가?
3. SBOM이 의사결정에 쓸 만큼 완전하고 최신인가?

## 4. 사용자별 사용 흐름

| 사용자 | 상황 | 시스템이 제공할 것 |
|---|---|---|
| 유지보수 엔지니어 | 출근 후 일일 점검 | 서버 상태와 해당 서버의 지원종료 구성요소를 한 화면에서 확인 |
| 보안·운영 담당자 | OS·미들웨어 취약점 또는 EOL 공지 확인 | purl/CPE로 구성요소를 찾아 영향 인프라를 역추적 |
| 운영 관리자 | 교체·업그레이드 계획 수립 | 하드웨어와 소프트웨어 위험을 합친 우선순위와 근거 URL |
| 기술지원 담당자 | OS·미들웨어 업그레이드 | 변경 전후 SBOM을 비교하고 영향 장비를 확인 |
| 계약 담당자 | 유지보수 갱신 | 장비 계약과 제품 지원종료 시점을 함께 확인 |

## 5. 기능 범위

### 핵심 MVP

- 인프라 자산 등록·조회·수정과 지원종료 위험도 계산
- 운영체제·펌웨어·하이퍼바이저·DBMS·백업·보안 에이전트 등록 및 자산 설치 관계 연결
- CycloneDX JSON SBOM 가져오기와 원본 보존
- 중첩된 구성요소와 의존관계 추출
- 구성요소 식별자(purl, CPE, bom-ref), 공급자, 버전, 라이선스 저장
- SBOM 품질 프로파일 검사와 누락 항목 표시
- 하드웨어·소프트웨어·구성요소의 통합 EOL 대시보드
- EOL/EOSL 날짜마다 제조사 또는 프로젝트 공식 근거 URL 저장

### 2단계

- SSH 점검으로 CPU·메모리·디스크·프로세스 상태 수집
- SSH에서 OS 패키지 목록을 수집하고 CycloneDX SBOM 생성
- 동일 제품의 SBOM 버전 간 구성요소 추가·삭제·버전 변경 비교
- OSV/NVD 등 취약점 소스 연동, CVE와 영향 자산 연결
- VEX를 이용해 실제 영향 여부와 조치 상태 기록
- CSV 자산 일괄 등록, PDF 리포트, Teams 알림

### 제외 범위

- 초 단위 실시간 모니터링
- SNMP/IPMI 하드웨어 센서 수집
- 애플리케이션 소스코드 자체 정적 분석 엔진 개발
- 상용 SCA 수준의 취약점 판정 정확도 보장
- 모든 SPDX/CycloneDX 버전 동시 지원

## 6. SBOM 품질 프로파일

가져온 문서는 다음 항목을 검사해 100점 환산 점수를 만든다.

| 검사 항목 | 의미 |
|---|---|
| 문서 일련번호 | 문서를 전역에서 구별할 수 있는가 |
| 생성 시각 | 어느 시점의 구성인지 판단할 수 있는가 |
| 작성자 또는 생성 도구 | SBOM 생성 주체를 알 수 있는가 |
| 구성요소 이름 | 구성요소를 사람이 식별할 수 있는가 |
| 구성요소 버전 | 영향 버전을 판정할 수 있는가 |
| 공급자 | 구성요소 공급 주체를 알 수 있는가 |
| 고유 식별자 | bom-ref, purl, CPE 중 하나가 있는가 |
| 의존관계 | 직접·간접 영향 범위를 계산할 수 있는가 |
| 라이선스 | 라이선스 검토에 필요한 정보가 있는가 |

이 점수는 CISA 최소 요소와 CycloneDX 권장 정보를 참고한 **EOLWatch 내부 품질 프로파일**이다. CycloneDX 스키마 적합성 인증이나 정부 조달 기준 충족을 의미하지 않는다. 추후 공식 JSON Schema 검증과 생성 도구별 호환성 테스트를 추가한다.

## 7. 위험도 기준

| 등급 | 지원종료일까지 | 조치 |
|---|---:|---|
| EXPIRED | 0일 미만 | 사용 현황 확인 후 즉시 교체·업그레이드 |
| CRITICAL | 0~180일 | 올해 예산과 작업 일정 확정 |
| WARN | 181~365일 | 다음 예산·업그레이드 계획에 반영 |
| SAFE | 366일 이상 | 정기 확인 |
| UNKNOWN | 날짜 또는 공식 근거 없음 | 공급사 공식 자료 조사 |

하드웨어와 소프트웨어에 같은 구간을 적용해 화면을 단순화한다. 실제 운영에서는 보안 업데이트 종료일과 부품 지원 종료일의 의미가 다르므로 `종료 유형`을 추가해 세분화할 수 있다.

## 8. 완료 기준

- 샘플 자산 30건, 관리 소프트웨어 10건을 등록할 수 있다.
- 서로 다른 생성 도구의 CycloneDX SBOM 5건 이상을 가져온다.
- 가져온 구성요소 수와 의존관계 수가 원본과 일치한다.
- 구성요소 검색 결과에서 연결 자산까지 3번 이하의 화면 조작으로 찾는다.
- 지원종료일이 지난 항목과 180일·365일 경계값을 정확히 분류한다.
- 품질 누락 항목을 화면 또는 API에서 확인할 수 있다.
- DB 백업 파일로 복구한 뒤 자산-SBOM 관계가 유지된다.

## 9. 조정 일정

| 주차 | 목표 | 결과물 |
|---|---|---|
| 1~2주 | 통합 데이터 모델, 자산·소프트웨어 API, SBOM 가져오기 | DB/API 및 샘플 SBOM |
| 3주 | SSH 운영 점검과 OS 패키지 수집 | 수집 이력 및 실패 분류 |
| 4주 | 통합 대시보드, 구성요소·영향 자산 탐색 | 외부 접속 가능한 웹 화면 |
| 5주 | 취약점 연동, PDF, 알림 | 일일 위험 리포트 |
| 6주 | 배포 안정화, 백업·복구, 보안 설정 | 운영 절차서와 복구 실증 |
| 7주 | 데이터 보강, 발표와 시연 | 최종 발표 자료 |

일정이 밀리면 취약점 자동 연동, 예산 리포트, Teams 알림 순서로 축소한다. 자산-SBOM 관계, SBOM 가져오기, 통합 위험도는 프로젝트의 차별점이므로 유지한다.

## 10. 시연 시나리오

1. 지원종료가 임박한 서버 한 대를 등록한다.
2. 그 서버의 운영체제·DBMS·주요 패키지를 담은 CycloneDX SBOM을 가져온다.
3. 시스템이 SBOM 품질과 구성요소·의존관계 수를 계산한다.
4. 특정 라이브러리에 지원종료일과 공식 출처를 입력한다.
5. 통합 현황에서 서버와 소프트웨어 위험이 함께 증가한 것을 확인한다.
6. 해당 구성요소에서 영향 자산과 애플리케이션을 역추적한다.
7. 일일 점검 결과와 함께 PDF 리포트를 발행한다.
