# EOLWatch 구현 현황

코드 기준: 2026-09-16. **웹에서 프로젝트 분석·SBOM 탐색·조치 업무·예약 분석·운영 백업을 사용하는 기능까지 구현했다.** 아래 구현 목록과 실제 실행 증거를 구분하며, 이번 확장의 배포·브라우저·복구 검증은 [기능 확장 검증 기록](PROJECT_EXPANSION_VERIFICATION.md)에 모은다. 기존 검증 당시의 숫자는 그 시점의 기록으로 보존한다.

추가 개발 후 전체 백엔드 394개·프런트엔드 120개 테스트가 통과했다. 전체 프로젝트 이력·저장 ZIP 재분석·취소·공개 EOL 일정 적용·현재 위험 집계를 추가했다. 사용법은 [프로젝트 이력과 EOL](PROJECT_HISTORY_AND_EOL.md)을 따른다. 실제 소스 ZIP·두 서버 분석·5분 예약·실패 후 재시도·관리 화면·백업 복구를 검증했고, EOLWatch 자체 직접 의존성을 갱신한 소스 재분석에서 CVE 9건→0건을 확인했다(미검출 8건, pytest 운영 의존성 제거 1건). 세부 범위와 번호는 확장 검증 기록을 따른다.

## 자산 편의성 확장 진행 상태

자산 모델과 화면에 재고자산 정보를 추가하고 SBOM/CVE 분석 결과를 자산 업무 화면에서 바로 판단할 수 있도록 1차 확장을 완료했다.

### 이번에 구현한 항목

- 자산명·자산번호·모델명·시리얼번호·건물·층·전산실·랙·랙 위치
- 구매일·구매가격·전력 사용량·전력 데이터 출처·보증종료일·담당자·담당 부서
- 운영 상태와 서비스 중요도
- 자산 목록의 이름·번호·모델·시리얼·IP·위치·담당자 검색과 상태·중요도 필터
- 자산 API의 CVE 심각도별 집계·총 CVE 수·내부 위험 점수·우선순위 등급
- 분석·SSH 점검·SBOM 저장·CVE 조치 이력을 묶은 자산 타임라인 API와 상세 표시
- 자산 상세의 기본 정보·소프트웨어·SBOM·타임라인 탭과 위험 요약 카드
- 자산 목록 상단의 위험 점수·CVE·EOL 기준 처리 우선순위 목록
- 자산 만료 알림, QR 현장 조회, CVE·SBOM·제품·계약 바로가기
- EOL·보증·유지보수 계약·미완료 CVE 조치 기한의 통합 알림 조회
- 자산별 월 전력비·연간 유지보수비 요약과 서버-소프트웨어 관계 표시
- 위험도 계산 결과 저장·조회 API와 산정 요소 이력
- 자산별 종합 PDF 보고서: 재고정보·위치·가격·전력·소프트웨어·SBOM·계약·분석 이력
- 기존 CSV 자산 등록에서 새 필드를 선택적으로 사용할 수 있는 호환성 유지

종합 위험도는 CVE 심각도, 지원 종료 임박도, 서비스 중요도, 운영 상태를 합산한 EOLWatch 내부 우선순위 점수다. CVSS나 실제 공격 가능성, 자동 조치 완료를 뜻하지 않으며 목록과 상세에서 산정 결과를 설명할 수 있도록 한다.

### 남은 자산 편의 기능

- 통합 기한 알림의 Teams 자동 발송과 알림 이력 화면 고도화
- CSV 자산 일괄 수정과 유효성 미리보기
- 여러 서버·DB·서비스를 한 번에 보는 전체 관계도
- 전력 단가·교체 비용을 관리자가 설정하는 예산 집계
- 자산 전용 상세에서 CVE 상세·EOL·계약의 세부 항목을 직접 펼쳐 보는 UI 고도화
- 종합 위험도에 계약 상태와 최근 점검 상태를 추가하고 가중치·계산 이력 저장

위 항목은 다음 구현 범위이며 현재 완료 기능과 혼동하지 않는다. 새 필드는 기존 분석 입력·자산 식별 스냅샷과 분리해 관리한다.

ZIP·일반 프로젝트 폴더는 포함된 잠금 파일·패키지 명세·설치 메타데이터를 읽는다. 대상 프로그램의 빌드·패키지 설치·실행은 하지 않는다. 데이터베이스에 예약을 저장하는 기능과 해당 실습 서버에 실제 예약이 등록·실행된 상태는 별개의 검증 항목이다.

## 이전 검증 시점의 실제 시연 증거

서비스: <http://127.0.0.1:18080> — 관리 VM DB. 맥의 <http://127.0.0.1:8080>은 별도 개발 DB다.

| 검증 | 대상·이력 | 결과 |
|---|---|---|
| 웹에서 OS 분석 | LAB-VM-02, 작업 #1 → 분석 #2 → SBOM #11 | 설치 패키지 669개, Grype 고유 CVE 3,216개·패키지 연결 12,241건 |
| 앱 업데이트 전 | LAB-VM-01, 작업 #2 → 분석 #3 → SBOM #12 | Jinja2 3.1.4, MarkupSafe 3.0.3, 앱 범위 CVE 3건 |
| 앱 업데이트 후 | LAB-VM-01, 작업 #3 → 분석 #4 → SBOM #13 | Jinja2 3.1.6, MarkupSafe 3.0.3, 앱 범위 CVE 0건 |
| 원본 전후 비교 | 분석 #3 → #4, 같은 `demo-python-venv` 범위 | 재분석 미검출 3건, 계속 검출·신규·구성요소 제거 0건 |
| 조치 기록 저장 | SBOM #12의 CVE-2025-27516, action #1 | admin 수동 FIXED, 분석 #4 근거 첨부, 새로고침 후 보존 |
| 비교 보고서 다운로드 | 실제 Chrome, 관리 VM의 분석 #3 → #4 | PDF 102,438바이트·JSON 4,011바이트, 브라우저·API 오류 없음 |

데모 앱은 실제 설치 라이브러리 2개를 수집했고 SPDX에는 대상 루트 항목을 포함해 구성요소 3개가 저장됐다. Syft·Grype 버전과 Grype DB 기준은 전후 동일했다. 앱의 HTTP 응답과 HTML 렌더링도 전후 확인했다.

**CVE 3건 → 0건은 지정한 데모 앱 가상환경에 한정된다.** 전체 OS 취약점 해소나 실제 악용 성공·차단의 증명이 아니다. 전후 비교 검증 시점에는 과거 CVE의 VEX가 `AFFECTED`로 남았으며 비교가 이를 자동 변경하지 않았다. 이후 CVE-2025-27516 한 건에는 분석 #4를 근거로 수동 `FIXED` 기록(action #1)이 추가됐다. 그 시점의 나머지 두 건은 `AFFECTED`였다. OS 대량 탐지 결과 역시 각 CVE의 실제 영향까지 확정한 결과는 아니다.

## 범위와 후속 검증

위 표의 ZIP·SSH 경로·조치 작업목록·예약 분석·백업 코드를 미개발 항목으로 다시 분류하지 않는다. 통합 완료 여부와 실제 시연 데이터는 [확장 검증 기록](PROJECT_EXPANSION_VERIFICATION.md)을 확인한다.

현재 범위 밖은 컨테이너 이미지/레지스트리 입력, Git URL에서의 자동 복제, 자동 패치·자동 조치 완료, 공개 다중 고객 SaaS의 조직별 데이터 격리다. 이를 구현했다고 설명하지 않는다. 예약 백업 도구는 기존 서비스 DB를 자동으로 덮어쓰는 재해 전환 도구가 아니다.

외부 공개 서비스 운영이나 다른 OS·CPU 조합의 추가 인증, 장기간 반복 운영 측정은 현재 로컬 검증과 별도의 작업이다. 교수님께 제출할 설명은 [현재 범위](SCOPE_V3.md), [전체 구조](ARCHITECTURE.md), [발표 안내](PROFESSOR_PROJECT_GUIDE.md)를 사용한다.
