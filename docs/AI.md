# AI 사용 범위와 데이터 정책

코드 기준: 2026-09-22. 교수님 지적 세 가지에 대한 답이다. "AI에 서버 구조를 넘기면 보안 위험이다", "CVE 대처 방안에 AI 어시스턴스가 있으면 좋겠다", "CVE 정보를 넘겨 AI가 오탐·과탐을 걸러 주는지 확인하라".

## 1. AI가 하는 일 다섯 가지 (전부 선택 기능)

| 기능 | 언제 | 보내는 것 | 받는 것 | 코드 |
|---|---|---|---|---|
| 검사 결과 요약 | 관리자가 버튼을 누를 때 | 라이브러리별로 묶은 CVE 상위 15개 | 위험 수준·먼저 손볼 것·확인 사항 (한국어 문단) | `ai_advisor.analysis_context` |
| SSH 점검 요약 | 관리자가 버튼을 누를 때 | OS·하드웨어 등급·가상화·포트·서비스·자원 사용률 | 환경 요약·눈여겨볼 점·다음 할 일 | `ai_advisor.check_context` |
| **AI 선별(triage)** | 관리자가 버튼을 누를 때 | KEV·EPSS 1% 이상·수정판 있는 일반 패키지·치명/높음 일반 패키지 CVE 최대 40건 + 서버 사실 | CVE마다 `해당` / `확인 필요` / `해당 없음 가능성` + 이유 + 조치 한 줄 | `ai_triage.generate_triage` |
| **AI 조치 가이드(advice)** | 조치 관리 창에서 버튼을 누를 때 | CVE 하나(패키지·버전·수정판·apt 대조·심각도·EPSS·KEV) + 서버 사실 | 해당 여부 근거, 명령 순서, 재시작 필요, 확인 방법, 완화책 | `ai_triage.generate_advice` |
| 검사 파이프라인 안 | 검사 중 자동 | (a) 잠금 파일 없는 소스의 import 이름·의존성 파일 앞부분, (b) SSH 점검 뒤 OS·플랫폼·포트·서비스와 명령 카탈로그 id | (a) 라이브러리·버전 추정 목록, (b) 실행할 카탈로그 id | `ai_library_reference`, `ai_collection` |

모두 `ai_advisor.complete()` 한 곳을 거치고, 같은 데이터·같은 모델이면 저장된 답을 재사용한다(`generate_record`, 프롬프트 SHA-256 캐시). `AI_PIPELINE=false`면 파이프라인 안 AI는 꺼지고, 키가 없으면 버튼 자체가 꺼진다.

## 2. AI에 넘기지 않는 것 (구조 노출 방지)

| 절대 보내지 않는 것 | 근거 코드 |
|---|---|
| 서버 IP·도메인, 호스트 이름 | `check_context`에서 제거(2026-09-22), `_server_facts`에 애초에 없음 |
| 클라우드 계정 번호·인스턴스 번호·AMI | `cloud`에서 `provider, instance_type, region`만 남김 |
| SSH 계정·비밀번호·개인키·호스트 키 | 어떤 컨텍스트에도 없음. DB에서도 암호문 |
| 설치 패키지 전체 목록 | 건수만(`packages: 669`) |
| 소스 코드 본문 | import 이름과 의존성 파일 앞 1,500자만 |
| 명령 문자열 | 수집 에이전트에는 카탈로그 id·목적만. AI는 명령을 쓰거나 고칠 수 없다 |

보내는 것은 "이 서버가 어떤 종류의 기계인가"를 판단하는 데 필요한 사실뿐이다. OS 이름과 버전, 실행 중 커널 버전, 아키텍처, 플랫폼 종류(aws/kvm/physical), 인스턴스 등급(t3.micro), 열린 포트 번호(15개까지), 실행 서비스 이름(12~15개까지), CPU 모델·코어·메모리 총량. 포트 번호와 서비스 이름은 "웹 서버가 있으니 그 CVE는 해당"과 같은 판정에 필요해서 남겼다. 이것마저 빼려면 `check_context`·`_server_facts`에서 `ports`·`services`를 지우면 되고, 판정 정확도가 그만큼 떨어진다.

확인 방법: 화면의 모든 AI 카드에 **"AI에 보내는 데이터 보기"** 버튼이 있다. 누르면 제공자로 나가는 전문이 그대로 보인다(`GET /api/ai/analyses/{id}/context`, `/triage/context`, `/checks/{id}/context`). 테스트 `test_check_context_never_carries_addresses_or_host_names`, `test_candidates_pick_only_findings_worth_a_look_and_hide_identifiers`가 호스트 이름·IP·인스턴스 번호·계정 번호가 프롬프트에 없음을 검사한다.

## 3. AI 선별이 오탐·과탐을 걸러 주는가

### 무엇을 보내나

5,000건을 다 보내지 않는다. 검사 결과에서 다음 조건에 드는 CVE만 후보로 고른다(`ai_triage.candidates`).

- KEV: CISA가 실제 악용을 확인한 CVE
- EPSS 1% 이상: 30일 안에 악용될 확률이 상위권
- 수정판이 있는 일반(커널 아닌) 패키지 CVE: apt로 지금 고칠 수 있는 것
- 치명·높음 심각도의 일반 패키지 CVE

정렬은 KEV → EPSS → 심각도 순이고 최대 40건을 보낸다. 후보마다 패키지·설치 버전·수정판·심각도·EPSS·KEV·apt 대조 결과·커널 여부·실행 중 커널에 속하는지를 붙인다.

### 무엇을 받나

CVE마다 세 판정 중 하나와 이유·조치 한 문장이다. `해당 없음 가능성`은 "이 서버 유형에 없는 장치·서브시스템, 실행되지 않는 커널, 이미 고쳐진 정황"처럼 근거가 있을 때만 쓰라고 시스템 프롬프트에 못 박았고, 확신이 없으면 `확인 필요`다. 후보 밖 CVE·정해진 값 밖 판정은 `validate_triage`가 버린다.

### 하지 않는 것

- 조치 상태(`vex_status`)를 바꾸지 않는다. 판정은 화면에 표시될 뿐이고, "영향 없음"으로 기록하는 것은 사람이 조치 관리에서 한다.
- 수천 건의 "수정판 없음 커널 CVE"를 AI에 보내 걸러 달라고 하지 않는다. 이것은 Ubuntu가 아직 고치지 않은 항목이라 AI가 아니라 배포판이 고쳐야 하며, 걸러야 할 대상은 `docs/KERNEL_CVE_VERIFICATION_2026-09-22.md`가 보여 주듯 실행 중 아닌 커널·해당 없는 장치 계열이다. 이것들은 AI 이전에 규칙(실행 커널 대조, 소스 단위 중복 접기)으로 줄이는 것이 맞고, AI는 그 뒤 남은 후보의 판단을 돕는다.

### 검증 결과

`docs/KERNEL_CVE_VERIFICATION_2026-09-22.md`: 도구 판정은 Ubuntu 추적기와 80건 중 78건 일치(불일치 2건은 DB 하루 지연). 즉 걸러야 할 "오탐"은 드물고, 문제는 "구분 없는 표시"였다. 그래서 EOLWatch는 (1) EPSS·KEV·risk를 저장해 배지와 개수로 보여 주고(검사 결과 표의 "실제 악용 확인 n개 · 악용 확률 1% 이상 n개"), (2) 후보만 AI에 보내 판정을 받고, (3) DB 시차 항목은 재검사로 사라진다는 안내를 한다.

## 4. 제공자와 비용

- 기본 OpenAI 호환 API(`OPENAI_BASE_URL`로 Gemini 사용 가능), `AI_PROVIDER=anthropic`이면 Claude. 키는 `.env` 또는 `*_FILE`(`docs/SECRETS.md`).
- 토큰 절감 수치는 `docs/TOKEN_DIET.md`. 선별 한 번은 후보 40건 기준 약 2,000~3,000자다.
- 무료 등급(Gemini 하루 20회)에서는 요약·선별·가이드가 요청 횟수를 나눠 쓴다. 같은 데이터는 캐시돼 다시 부르지 않는다.

## 5. 한계

- 판정은 확률적이다. 같은 입력에 다른 답이 나올 수 있어 `다시 선별`이 있고, 결과에 모델·시각·토큰이 남는다.
- 서버의 로드된 커널 모듈(`lsmod`)은 아직 보내지 않는다. 드라이버 계열 CVE의 "해당 없음" 판정 정확도를 올리려면 SSH 점검에 `lsmod` 수집을 추가해야 한다(카탈로그 한 줄).
- 제공자에게 보낸 데이터는 제공자 약관을 따른다. 고객사 서버를 대신 검사하는 형태라면 `docs/LICENSES_AND_TARGET.md`의 확인 항목을 본다.
