# 실제 운영에서 어떻게 쓰나 (실사용 가이드)

코드 기준: 2026-09-22. 교수님 지적 "개념적인 부분이 실질적으로 사용 가능한지"에 대한 답이다. 한 팀이 EOLWatch를 일주일 단위로 굴린다고 가정하고, 화면 이름과 API를 그대로 써서 적는다. 여기 적힌 흐름은 2026-09-21~22에 실제 서버(EC2 3대, 학교 서버 1대, 실습 VM 1대)로 돌려 본 것이다.

## 1. 누가 쓰나

| 역할 | 계정 | 하는 일 |
|---|---|---|
| 운영 담당(ADMIN) | 관리자 | 서버 등록, 검사 실행, 조치 기록, AI 요청 |
| 검토자(VIEWER) | 조회자 | 결과·비교·보고서 열람, 조치 이력 확인 |

조회자 계정은 `POST /api/auth/users`로 만든다. 화면에는 계정 관리 메뉴가 없다.

## 2. 처음 한 번: 설치와 서버 등록 (30분)

1. 관리 서버(리눅스 VM 또는 PC)에 Docker를 설치하고 저장소를 받는다.
2. `.env`를 만든다. `JWT_SECRET`, `CREDENTIAL_KEY`(서로 다른 무작위 값), `ADMIN_PASSWORD`, AI를 쓰면 `OPENAI_API_KEY`. 절차와 보호 방법은 `docs/SECRETS.md`.
3. `docker compose up --build -d`. api가 마이그레이션을 적용하고 관리자 계정을 만든다.
4. 대상 서버마다 검사 전용 계정을 만든다. 필요한 권한은 읽기와 `sudo -n apt-get update`뿐이다. 계정의 홈 디렉터리에 Syft 실행 파일(약 100 MB)이 복사된다.
5. `인프라 검사 → + 서버 등록`. 주소, SSH 포트, 계정, 인증 방식(비밀번호 / 개인키 첨부 / 관리 서버 키)을 넣는다. 첫 접속 때 호스트 키를 기억한다.
6. 개발팀 소스는 `개발 검사`에서 대상(프로젝트 묶음)을 만들고 ZIP·의존성 파일·Git 주소로 올린다.

## 3. 매주 반복: 검사 → 선별 → 조치 → 확인 (서버 1대당 10분)

| 순서 | 화면 | 하는 일 | 걸리는 시간 |
|---|---|---|---|
| 1 | 인프라 검사 → SSH 점검 | 자원 사용률·OS·실행 커널·포트·서비스 수집. 수집 에이전트가 미적용 업데이트·재부팅 대기·SSH 정책·방화벽을 확인 | 10~30초 |
| 2 | 인프라 검사 → 취약점 검사 | Syft로 설치 패키지 → SPDX → Grype 대조 → apt 대조. 완료되면 결과 화면이 열림 | 1~3분 |
| 3 | 검사 기록 → CVE 결과·조치 | 결과 표의 첫 줄을 본다: **지금 고칠 수 있는 CVE(커널 제외) / 실제 악용 확인(KEV) / 악용 확률 1% 이상**, 그리고 2차 검증 줄: **수정 예정 n(다음 커널) · 업스트림만 수정 n · 이미 수정됨(DB 지연) n · 이 서버 미해당 추정 n**. 목록 기본 범위는 "조치 대상만"이라 수천 건이 한꺼번에 뜨지 않는다 | 1분 |
| 4 | 같은 화면 → AI 선별 실행 | 후보(KEV·EPSS·수정판·심각도)만 보내 `해당 / 확인 필요 / 해당 없음 가능성`과 조치 한 줄을 받는다 | 10~20초 |
| 5 | 서버에서 조치 | 보통 `sudo apt update && sudo apt upgrade`, 커널이면 재부팅 후 `sudo apt autoremove --purge`. 조치 관리 창의 **AI 조치 가이드**가 명령·재시작·확인 방법을 써 준다 | 서버마다 다름 |
| 6 | 검사 기록 → 조치 관리 | CVE(또는 패키지)마다 상태와 메모를 기록. `해당 없음 가능성`으로 판정된 것은 사람이 확인한 뒤 "영향 없음"으로 기록 | 5분 |
| 7 | 인프라 검사 → 취약점 검사 | 재검사 | 1~3분 |
| 8 | 검사 기록 → 검사 전후 비교 | 이전·이후 검사를 골라 계속 검출/새로 검출/재검사 미검출/구성요소 제거를 본다. PDF·JSON을 내려받아 보고 | 2분 |

### 실제 예: srv-my (EC2, Ubuntu 26.04), 2026-09-22

| 단계 | 값 |
|---|---|
| 검사 #40 | CVE 5,150 · 커널 4,778 · 지금 고칠 수 있음 2 · KEV 2 · EPSS 1% 이상 28 |
| 읽기 | KEV 2건은 이전 커널 1006에 붙어 있고 1012에서 수정됨. 일반 패키지 2건(coreutils)은 apt 대조 "오탐 의심" |
| 조치 | 재부팅 → `apt autoremove --purge`(이전 커널 제거), coreutils 2건은 "영향 없음" 기록 |
| 실제 재검사 #50 | **3,498건**(커널 3,126은 전부 Ubuntu 미수정), **KEV 0**, 수정판 있는 커널 CVE 1,652 → 0. `autoremove`는 AMI 기본 커널을 안 지우므로 `apt-get purge 'linux-*-7.0.0-1006*'`가 필요했다 |

실습 VM에서 같은 절차를 실제로 돌린 결과(3,904 → 3,896, apt가 올릴 수 있다고 한 8건만 사라짐)는 `docs/KERNEL_CVE_VERIFICATION_2026-09-22.md` 2절에 있다.

## 4. 숫자를 읽는 규칙 (팀 안에서 합의할 것)

1. **KEV가 있으면 그날 처리한다.** 실제 악용이 확인된 것이다.
2. **"지금 고칠 수 있는 CVE(커널 제외)"는 이번 주 안에 0으로 만든다.** apt 한 번이면 된다.
3. **커널 CVE는 이전 커널 정리와 재부팅으로 줄이고, 나머지는 Ubuntu 수정판을 기다린다.** unattended-upgrades를 켜 두면 자동으로 줄어든다.
4. **"수정판 없음"은 조치 대상이 아니라 감시 대상이다.** 매주 재검사에서 줄어드는지만 본다.
5. **"오탐 의심"(저장소에 업데이트 없음)은 담당자가 확인 후 "영향 없음"으로 기록한다.** Grype DB가 하루 늦는 경우가 대부분이다.
6. **미검출은 조치 완료가 아니다.** 조치 완료는 사람이 기록한다.

## 5. 운영 항목

| 주기 | 일 | 근거 |
|---|---|---|
| 매일 08:30 | 등록 서버 SSH 점검 자동 실행(`monitored` 서버) | `worker.py` cron |
| 매일 | DB·업로드 ZIP 백업 + 임시 DB 복원 검증 | `scripts/backup-runtime.py --verify-restore --install-schedule` |
| 검사 때마다 | Grype DB 자동 갱신(새 빌드가 있으면) | 검사 결과에 DB 빌드 시각 저장 |
| 분기 | Syft·Grype 버전 확인 | `docs/SCANNER_OPTIONS.md` |
| 필요 시 | `.env` 키 교체 | `docs/SECRETS.md` |

## 6. 이 도구가 하지 않는 것 (기대를 맞추기 위해)

- 자동 패치를 하지 않는다. 명령은 사람이 실행한다.
- 실행 중인 프로세스가 실제로 취약한 코드 경로를 쓰는지 판단하지 않는다. 패키지 단위 판정이다.
- 컨테이너 이미지·Windows·네트워크 장비는 대상이 아니다. SSH 가능한 Ubuntu/Debian(dpkg) 서버와 소스 ZIP·Git이 대상이다.
- 여러 고객사를 한 인스턴스에서 분리해 운영하는 기능이 없다. 고객사별로 인스턴스를 따로 띄운다(`docs/LICENSES_AND_TARGET.md`).
